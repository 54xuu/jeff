# 手机打开会话看不到记录、电脑提示「消息过于频繁」

版本：1.9.5（PATCH）

## 现象

在 Android App 里点开一个会话，对话区一片空白；同时电脑「设置 → 远程控制」页出现错误「消息过于频繁」。

## 根因

三件事叠在一起：

1. **电脑攒了一批推送，握手成功那一刻一次性全发。** `RemoteGateway.push()` 在手机加密通道没建立时，把 `chat-stream` / `data-changed` / `sidecar-status` 等推送塞进队列（最多 40 条）；手机一握手（`secure` 事件），`flush()` 在同一毫秒把握手回包加 40 条推送全部发出。电脑聊着天时，一轮回复的流式帧就能把队列攒满。
2. **中转站超限直接丢帧。** `apps/relay/src/hub.ts` 每条连接 1 秒最多 30 帧，超出的帧不转发，只回一个 `rate`「消息过于频繁」给电脑——所以错误出现在电脑上。
3. **会话密文要求序号严格连续。** `RemoteCipher.open()` 与原生层 `NoteWatch.openText()` 都只接受 `n == recvN`。中间丢了 8～11 帧后，手机后续收到的每一帧（包括 `chat:history` 的回应）都序号不符：JS 抛「序号不符」，原生层直接静默丢弃。于是请求超时、会话空白，而且这条通道此后永久失效。

什么时候会先进入「电脑在线、手机通道没建立」的状态？排查中又找到两处让通道长期失效的缺口，正是触发队列积压的前提：

- **电脑重启后**，手机的 `RelayLink` 还拿着旧会话密钥，`hello()` 见 `peer.session` 存在就直接返回，不会重新握手；电脑新链路把手机的请求当握手帧去解，失败。
- **手机重开（进程被杀、重连）后**，手机用新的引导密钥从零发 `hs`，电脑因为 `peer.session` 还在，拿旧会话密钥去解，失败，握手超时。

另外顺手发现：`group:history` 返回 `{ threadId, messages }`，App 却当数组用，**项目群会话本身就显示不出历史**。

## 修复

| 位置 | 改动 |
|---|---|
| `packages/core/src/remote/link.ts` | `RelayLink` 出站限速：所有帧进 FIFO，1.25 秒窗口内最多 20 帧（中转站是 1 秒 30 帧；窗口放宽避免两批帧卡在秒边界上被算进同一秒——第一版按 1 秒窗口就踩了这个坑，61 帧压测稳定复现） |
| 同上 | 新增 `resetPeer(peerId)`：丢弃旧会话、换新引导密钥，握手进行中不打断 |
| 同上 | 电脑端 `rehello`：旧会话解不开时，用新引导密钥再试一次，是 `hs` 就换新会话 |
| `apps/desktop/src/main/remote/gateway.ts` | 离线队列不再存 `chat-stream`（没前文的增量没用，手机进会话会重拉历史），同内容去重，上限 20 |
| `apps/mobile/src/session.ts` | 收到电脑上线通知（电脑换了链路）→ `rekey`：先 `Native.disarmRecv` 收回原生解密，再重新握手；`hello()` 等 rekey 完成 |
| `apps/mobile/src/App.tsx` | `group:history` 兼容 `{ threadId, messages }`，缓存读取同样兼容 |

中转站代码没改，不需要重新部署。

## 测试

新增 `apps/relay/test/link.test.ts` 四例（真中转站 + 真 `RelayLink`）：

- 电脑一口气推 61 帧，手机全部收到、后续请求正常回应、两端没有错误（修复前：电脑收到一串「消息过于频繁」，手机「序号不符：期望 30，收到 39」，请求超时——和现场一致）
- 手机用同一身份重连后重新握手能继续调用
- 电脑重启后手机 `resetPeer` + `hello` 能继续调用
- App 真实的 `PhoneLink`：电脑重启后不用重开 App 也能继续调用（已确认回退 `session.ts` 后此例失败）

回归：`npm test`（core 357 + relay 11 全绿，relay 套件连跑 5 次稳定）、core/desktop/mobile 包级 `tsc` 通过、`test:e2e` / `v18` / `cron` / `remote`（含真模型回复一例）全绿。
