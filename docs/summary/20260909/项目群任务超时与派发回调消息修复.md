# 项目群任务超时与派发回调消息修复（v1.7.15）

- 日期：2026-09-09
- 版本：v1.7.14 → **v1.7.15**（PATCH，同步根/core/desktop 三处 `package.json`、`package-lock.json`，并补齐漂移的 `packages/core/src/version.ts`）
- 平台：Linux（AppImage + deb）、Windows（NSIS，wine64 打包）

## 问题一：群任务执行报「处理消息失败：The operation was aborted due to timeout」

### 现场与根因

- 日志：`.tmp/logs/debug-20260909.log`。失败的「项经理」回合从 `20:01:18.037` 到 `20:11:18.054`，间隔约 **600,017ms**，与 `OcClient.sendMessage()` 默认 `timeoutMs=600000` 精确吻合。
- 错误由 `AbortSignal.timeout(timeoutMs)` 触发（`TimeoutError`），**不是**用户点击停止（无 `group-send-stop`/`abort-fail`），**不是**先前已修复的 Undici `HeadersTimeout`（默认 300s，v1.7.11 已关为 0），也**不是** `jeff_delegate` 子调用失败（无 `delegate-fail`）。
- 普通群流水线（leader 首回合 / `@成员` worker 回合 / leader 总结）此前未显式传超时，继承默认 10 分钟；长任务（读逐字稿、产出文档）超过 10 分钟即在预算终点被掐断。
- 次要因素：日志 `20:03:06` 记录了活跃回合期间由 registry dirty 触发的 sidecar 重启（`GroupChat.doEnsureSession → restartIfRegistryDirty`）。它不是本次精确 600s 超时的直接错误类型，但会打断在途请求，本次一并防护。

### 修复

1. **统一 30 分钟回合预算**：`group.ts` 新增导出 `GROUP_TURN_TIMEOUT_MS = 30*60*1000`，`runTurn()` 显式传给 `sendMessage()`；`delegate.ts` 的 `DELEGATE_TIMEOUT_MS` 改为引用同一常量，两条任务路径不再漂移。超时后仍不自动重放 POST（任务有副作用，防重复执行）；用户主动停止的判定逻辑不变。
2. **sidecar 重启延迟落闸**：`restartIfRegistryDirty()` 遇到在途群工作（`GroupChat.hasBusyPipeline()` 或 `Delegator.activeCount>0`）时挂起 `pendingRegistryRestart`，由流水线 `onPipelineIdle` / 委派 `onIdle` 回调在空闲后触发重启；不再把长任务打断。

## 问题二：任务派发/回调显示为中间灰色小字且不完整

### 根因

- 灰色小字由 `sender_type: 'system'` 决定（`GroupWindow.tsx` 渲染分支 + `.msg-system` 样式）：
  - `jeff_delegate` 派发公告是 system 消息，且指令被 `slice(0, 120)` 截断（附录A 中「🔗 项经理 委派任务给 项小沐：…」即此）；
  - 委派失败回调也是 system 消息，错误被截 300 字；
  - 普通流水线 leader 拆解后还有一条冗余的「📋 已拆解任务，开始按序派发…」灰色公告。
- worker 汇报提示词要求 `@leader`，而需求是 `@发起任务的用户`（本产品单真人身份，即 `@我`）。

### 修复

| 消息 | 改后形态 |
|---|---|
| 委派派发 | leader **普通气泡**：`@我 已将任务派发给 @<成员>，任务要求如下：<完整指令>`，不截断；`meta.phase='dispatch'` |
| 委派成功回调 | worker **普通气泡**：`ensureCallbackMention()` 确保含 `@我`；完整 resultText；`meta.phase='result'` |
| 委派失败回调 | worker **普通气泡**：`@我 任务执行失败：<完整错误 message>`，不截断；堆栈只进调试日志；`meta.phase='failed'` |
| 流水线 worker 回调 | 落库前 `ensureCallbackMention()` 兜底补 `@我`（模型未按约定输出也不丢语义）；briefing 与派发 prompt 的汇报对象由 `@leader` 改为 `@我` |
| 「已拆解任务」公告 | 删除：派发内容已由 leader 普通消息完整承载 |

- 直连 worker 场景的 leader 自动总结不再依赖 `@leader` 提及判断（worker 回调对象已改为 `@我`），改为直连执行完成即触发。
- 前端零改动：agent 消息分支本就提供头像/名称/完整 Markdown 气泡。
- 附带修复：主进程补上 `core.bus.on('group-updated') → broadcast` 转发（此前委派写库后渲染层拿不到即时事件）；Delegator 通知携带冻结的 `{projectId, threadId}`，防切换会话后刷错线。

## 已知限制 / 后续

- 直连 worker（用户 `@worker` 直接派活）完成后，leader 总结现在必然触发（旧逻辑仅在 worker 回复含 `@leader` 时触发；提示词改造后该信号已不可靠）。若希望直连「快问快答」不唤醒 leader，需要再引入任务类型区分。
- sidecar 重启延迟只覆盖项目群工作（流水线/委派）；私聊回合在途时重启仍会发生，后续可按需扩展。
- 结构化 mention（可点击、多真人用户身份）未引入；当前 `@我` 为单用户显示约定，文本协议即可满足。
