# 项目群协作能力评估与项目规则统一（v1.7.13）

日期：2026-09-09 · 版本：1.7.13（PATCH） · 分支：main

## 背景与目标

本次处理两件事：

1. **如实评估**「项目群由 leader 拆解任务、`@` 对应 agent 执行」思路以 OpenCode sidecar 为基座是否满足要求、有哪些缺陷（只评估，不建设新调度系统）。
2. **统一项目级 AGENTS.md**：设置 → 记忆里按项目保存在 `~/.jeff/agents-md/<projectId>.md` 的文件与项目工作空间目录下的 `AGENTS.md` 两处并存，明确以设置界面这份（可 WebDAV 同步的权威副本）为唯一执行来源。

## 一、OpenCode 基座能否支撑「leader 派任务 @ agent」——如实结论

### 已具备、可直接跑通的能力

群聊协作主闭环已在 `packages/core/src/orchestrator/group.ts` 实现，并有单测与真实 sidecar E2E 覆盖：

- 群消息默认路由 leader；用户可 `@成员名` 直达（`parseMention` 支持最长名匹配、去重）。
- leader 回复中写 `@成员名 任务说明`，调度器解析全部提及，按出现顺序**串行**驱动各 worker 的独立 OpenCode session 执行；worker 结果回群后可继续 `@` 其他 worker 续入队列。
- 队列执行完毕自动唤醒 leader 验收总结；单条流水线最多 5 hop 防死循环。
- leader 还可用 `jeff_delegate` 工具做结构化委派（leader 权限校验、并发去重、单消息上限 5 次），worker 结果既回群也作为工具输出同轮返还 leader。
- 会话按「项目 × 群话题 × agent」隔离（`session:group:<projectId>:<threadId>:<agentId>`），同一项目流水线串行避免工作空间文件/git 冲突，不同项目并行。
- sidecar 崩溃自动重启（最多 5 次退避）、健康检查、端口代际重绑、10 分钟请求总预算、SSE 流式回传均已就绪。

### 缺陷与边界（本次如实记录，未在本次修复的项会作为后续路线）

按用户确认的范围（**仅评估并修规则，不建设持久任务调度**），以下边界如实用途上要心中有数：

| # | 缺陷 | 现状说明 |
|---|------|----------|
| 1 | **任务卡与执行不联动** | `task.assignee_id` 只是一条数据；`jeff_task_create/update` 不会启动任何 agent 执行。当前「@ 派工」是即时会话编排，不是任务系统派工。UI 的任务看板也已移除（E2E 显式断言无看板；README 中「看板拖拽」表述已过时）。 |
| 2 | **无持久化执行实例** | 没有 run/job 记录、重试、失败原因、超时恢复；应用/sidecar 中断后在途工作不可恢复。 |
| 3 | **任务与消息/会话/产物无审计关联** | 无法从 JEF-n 追溯对应指令、session、worker 汇报与验收。 |
| 4 | **@ 文本协议脆弱** | 用户消息只取第一个有效 `@` 作为初始路由；leader 回复里讨论性的 `@`、代码块中的 `@`、重名/前缀名可能被误判为派发；任务内容只是提及之间的文本切片，无法表达验收标准/依赖。 |
| 5 | **worker 失败中断全链路** | worker 阶段失败会 reject 余下队列与 leader 总结（仅 leader 总结失败有部分成功保留 + 手动重试提示）。 |
| 6 | **并发锁只按 projectId** | 两个项目配置同一 `workspace_dir` 时仍可能并行写同一目录，缺 workspace 级互斥。 |
| 7 | **任务/项目工具无 leader-only 授权** | `jeff_project_*` / `jeff_task_*` 不校验调用者是否 leader（仅 `jeff_delegate` 校验）；worker 模型主动调用也能改任务。 |
| 8 | **隔离是会话级不是安全域级** | 多 agent 共享单个 sidecar 进程；全局用户级规则、agent 跨项目记忆仍构成跨项目上下文通路。不适合强隔离场景。 |

**结论**：作为「即时群聊协作编排」当前可用且已验证；若未来要升级为「项目任务调度系统」，需要单独设计 `task_run` 执行实例、状态机、幂等与恢复、结果关联、workspace 资源锁、依赖图与权限模型，而不是继续强化文本 `@` 解析。本次不实现。

### 本次顺带修复的协作缺口：委派回合规则注入

leader 用 `jeff_delegate` 委派时，worker 之前只拿到群 briefing，**用户级/项目级 AGENTS.md 与记忆都不注入**（`Delegator.memberBriefing` 不走 `buildMemorySystem`）。已修复：

- `Delegator` 增加 `buildMemory?: (agentId, projectId) => string | undefined` 注入点，由 `JeffCore` 绑定到 `buildMemorySystem`；
- 委派 worker 的 `system` 变为 `briefing + 规则/记忆块`，与普通群回合语义一致；
- 未注入时退化为仅 briefing，向后兼容；
- 新增 2 个 delegate 单测断言注入顺序与兼容行为。

## 二、项目级 AGENTS.md 唯一来源改造

### 改造前的问题

- `agentsMdBlocks` 把权威副本（`~/.jeff/agents-md/<projectId>.md`）与工作空间 `<workspace>/AGENTS.md` **同时注入**，且工作空间块排在后面，冲突时模型倾向遵循后出现的规则；
- 设置页保存只写权威副本、同步只上传权威副本，但工作空间旧文件继续生效 → 本机与另一台机器执行规则不一致；
- 设置页文案仍称「项目级放在各群工作空间目录下」，与 v1.7.0 起的权威副本设计相悖，误导用户。

### 改造后的语义（与用户建议一致：以设置界面这份为准）

`composeAgentsMdBlocks`（从 `JeffCore.agentsMdBlocks` 抽出的可单测纯函数，`packages/core/src/index.ts`）：

1. 用户级 `~/.jeff/AGENTS.md`：注入全部对话（含私聊）。
2. 项目级：存在权威副本 `~/.jeff/agents-md/<projectId>.md` 时**只注入它**，工作空间文件不再读取。
3. 权威副本缺失时，兼容读取工作空间旧 `AGENTS.md` 作为一次性迁移来源（注入块标注「项目级」与实际路径）；设置页编辑保存后即写入权威副本，此后工作空间文件不再生效。
4. WebDAV 同步协议不变（远端 `agents-md/project-<id>.md`，LWW），`workspace_dir` 仍按设备保留。

同步修正的文案：

- 设置 → 记忆页说明（`MemorySettings.tsx`）：改为「项目级按项目保存在 Jeff 数据目录（agents-md/）下……随 WebDAV 同步；旧工作空间文件仅在项目规则尚未创建时作为迁移来源」。
- 内置 `jeff-usage` skill 的 AGENTS.md 段落（`writeUsageSkill`）同步改为同一语义。
