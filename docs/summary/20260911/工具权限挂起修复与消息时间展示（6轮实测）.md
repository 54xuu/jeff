## 二、根因：opencode 权限求值「未命中 = ask」，而 Jeff 没有确认 UI

opencode 二进制里的权限求值函数：

```js
function evaluate(permission, pattern, ...rulesets) {
  return rulesets.flat().findLast(r => match(permission, r.permission) && match(pattern, r.pattern))
      ?? { action: "ask", permission, pattern: "*" }   // ← 未命中规则时默认 ask
}
```

`Permission.ask` 随后 `publish(Asked)` 并 `await` 用户回复（**没有超时**）。Jeff 桌面端从未监听
`permission.asked`，也没实现确认弹窗，于是请求一直挂着，直到 `OcClient.sendMessage` 的 10 分钟
`AbortSignal.timeout` 把它掐掉 → 用户看到的 `TimeoutError`。

而 `packages/core/src/oc/configWriter.ts` 原来只写了：

```json
"permission": { "edit": "allow", "bash": "allow", "webfetch": "allow" }
```

**判定性复现**（`.tmp/perm-repro/perm-repro.mjs`，直连 sidecar，不依赖界面）：

| 场景 | 权限配置 | 结果 |
|------|----------|------|
| 读**项目外**绝对路径文件 | 修复前（仅 edit/bash/webfetch） | 90s 超时；SSE 收到 `permission.asked {"permission":"external_directory","patterns":["/home/xujian/cdbox/live-ext/*"]}`，`read` 停在 `running` |
| 读**项目外**绝对路径文件 | 修复后 | 无任何 permission 事件，14.9s 读完并正确回答 |
| 要求模型调用 `question` 工具 | `question: allow` | 90s 超时；SSE 收到 `question.asked`，永久等待用户作答 |
| 要求模型调用 `question` 工具 | `question: deny` | 7.7s 完成；工具被 opencode 直接从可用列表移除，模型改用文字回答 |

> 注意：**放在 `/tmp` 或项目工作树内的文件不会触发** `external_directory`（opencode 默认放行
> `tmp/*` 与项目目录），所以复现必须用「仓库之外、非 /tmp」的绝对路径——这也是为什么这个 bug 只在
> 用户真机上（Windows 跨盘符 `D:\P_xujian\...`）暴露。

### 修复

1. **`configWriter.ts` 权限全量放行**：`"*": "allow"` + 逐个工具显式 `allow`
   （`read / edit / glob / grep / list / bash / task / external_directory / todowrite / webfetch /
   websearch / lsp / skill / doom_loop`）。
2. **交互型权限必须 `deny`**：`question / plan_enter / plan_exit` 置为 `deny`。这三项不是「允许执行工具」，
   而是「允许向用户提问 / 切换计划模式」——设成 `allow` 等于又造一个永久挂起点。`deny` 会让工具
   快速失败并把原因回给模型，与 opencode 自身非交互 CLI 的行为一致。
3. **兜底防线**：`JeffCore.handleOcEvent` 新增对 `permission.asked` / `question.asked` 的处理——
   收到即调 `POST /permission/{id}/reply {reply:"once"}` 自动放行、`POST /question/{id}/reject` 自动拒绝，
   并落 `permission-auto-allow` / `question-auto-reject` 日志。即使将来某个 agent 级权限规则绕过配置，
   也不会再干等 10 分钟。

## 三、排查现场：日志与入口（回答用户第 3 问）

- **调试日志默认开启**（原为默认关闭）。卡死/超时这类问题只有事前开着才留得下现场，事后无法补录。
  可在「设置 → 引擎服务」关闭。
- 新增工具调用打点（`packages/core/src/index.ts#logToolPart`）：按 part 状态迁移记录
  `tool-pending` / `tool-start` / `tool-done` / `tool-error`，含 `tool`、`callId`、`elapsedMs`、
  入参/输出摘要（截断）。排查「卡死」时只需看日志里哪个工具长时间停在 `pending`（等授权/等交互）。
- 新增中断留痕：`abort`（发出中断）、`chat-stop-req`（停止请求到达主进程、是否匹配到会话、是否是
  延迟中断）、`abort-fail`。
- 「设置 → 引擎服务」新增 **「打开日志目录」** 按钮（`debugLog:openDir`）。

**出问题时请提供**：`<数据目录>/logs/debug-YYYYMMDD.log`（设置页一键打开目录），以及出问题的
消息文字/截图（现在消息都带时间戳，能直接对上日志时间）。

## 四、消息发送时间展示

- 新增 `apps/desktop/src/renderer/src/format.ts` 的 `fmtFullTime`：本地时区 `YYYY-MM-DD HH:mm:ss`。
- **智能体/群成员消息**：发送人名字右侧显示时间；**自己发的消息**：气泡上方右对齐显示时间；
  **流式气泡**：显示本轮触发时间（取最近一条用户消息的时间）。
- 样式只吃主题变量（`.msg-time { color: var(--text-reasoning); font-variant-numeric: tabular-nums }`），
  自动适配 `themePack × light/dark`；双主题实测取到 `rgb(163,163,163)`（亮）/ `rgb(117,117,117)`（暗）。
- **语义修正**：智能体消息的时间取 opencode 的 `time.completed`（回复完成时刻）而不是 `created`
  （消息创建时刻）。群聊落库本就是在回复完成后写 `created_at`，这样两边语义一致；
  用 `created` 会把思考 + 工具的耗时全部漏掉，无法量「这一轮花了多久」。

## 五、实测中发现并修复的其它缺陷

### 1. 停止按钮「点了没反应」——私聊存在会话建立竞态（用户报告同源场景）

界面上的「发送中」是**同步**置位的，所以「停止」按钮在 `ensureSession` 建会话期间（首条消息冷启动
可达数秒）就可点；而 `IPC.chatStop` 原来是：

```ts
const sessionId = core.privateChat.getSessionId(agentId)
if (sessionId) await core.oc.abortSession(sessionId)   // sessionId 为 null 时静默丢弃
```

实测日志（真凶）：

```
10:58:45.401 [chat-stop-req] sessionId: null      ← 用户点停止（会话还没建好）
10:58:46.058 [send-start]    sessionId: ses_...   ← 0.66 秒后会话才创建完成
```

**修复**：`PrivateChat.stop()` 在会话未建好时把停止记成**意图**（`pendingStop`），
`send` 在建好会话后立即以 `PrivateChatStoppedError(sessionId, cancelled=true)` 收尾（请求根本不发出）；
已建好会话时照旧 `abortSession`。`pendingStop` 只在 `inFlight` 时记录，且 `send` 结束即清理，
空闲时点停止不会污染下一轮。群聊本就有 `runState.cancelled` + 会话回退，未受影响。

### 2. 「已停止 / 发送失败」提示会被历史重拉整段冲掉

`loadHistory` 是整段替换，而回复结束时服务端会推 `chat-updated` 触发重拉，与提示写入几乎同时发生 →
提示被冲掉，用户完全看不到反馈（强化了上面「点了停止像没反应」的观感）。同时，被取消的那一轮
（请求没发出去）用户消息也不在引擎历史里，重拉后**用户刚敲的内容凭空消失**。

**修复**：`store.loadHistory` 改为合并而不是替换（`mergeLocalMessages`）：服务端为准；本地条目里
乐观用户消息若已被服务端回显则丢弃，否则保留；提示类与未被回显的用户消息**按时间插回原位置**
（不能统一追加到末尾，否则时间线错乱）。切换会话 / 新建会话时传 `resetLocal` 清掉旧提示。

### 3. 私聊的系统消息被当成智能体说的话

`⏹️ 已停止生成` / `⚠️ 发送失败` 在私聊里走的是「助手气泡」分支，会带着智能体名字和头像渲染，
看起来像「文档小沃说：已停止生成」。改为与群聊一致的居中提示条，并同样带上时间戳。

## 六、6 轮真实模型实测（全部通过）

测试台：`.tmp/live7/`（`seed7.mjs` + `live7.spec.ts`，已 gitignore）。
每轮都额外断言：**每条消息都带 `YYYY-MM-DD HH:mm:ss`、智能体消息同时有名字与时间**。

| 轮次 | 场景 | 结果 | 关键证据 |
|------|------|------|----------|
| R1 | 私聊读**项目外**绝对路径文件（复现附录 A） | ✅ 36s | 无 `permission.asked`；日志 `tool-pending→tool-start→tool-done(read)` 带入参与输出；答案含文件独有内容 `MQTT` |
| R2 | 私聊纯文本问答（思考 + 正文落库） | ✅ 59s | 流式最长正文片段完成后仍能在落库正文里找到 |
| R3 | 私聊多工具（`read` 数据.csv → `write` 汇总.md） | ✅ 46s | 工具 `[read, write]`；文件生成且含总分 `255` |
| R4 | 主动停止 ×2（刚发出就停 / 流式中停） | ✅ 44s | 两条「⏹️ 已停止生成」按时间线正确插入；无「发送失败」；停止后仍可正常对话 |
| R5 | 项目群派发协作 | ✅ 1.8m | 3 条智能体消息（指挥官派发 → 执行员甲 `glob/read` 汇报 → 指挥官汇总 255），群内时间戳齐全 |
| R6 | **权限兜底**：把 opencode.json 改回旧权限并重启引擎 | ✅ 59s | 日志出现 `permission-auto-allow`（`external_directory`），读取仍成功 → 兜底防线有效 |
| 附加 | 时间戳暗/亮双主题视觉 | ✅ 44s | 两主题颜色分别 `rgb(163,163,163)` / `rgb(117,117,117)`，格式全部匹配 |

单测补充（无需真实模型）：`configwriter.test.ts` 断言权限放行/deny 组合与「不出现 ask」；
`private-model.test.ts` 断言「会话建成前点停止 → 保留意图、不发出请求、抛可辨识的停止错误」
与「空闲时点停止不污染下一轮」。
