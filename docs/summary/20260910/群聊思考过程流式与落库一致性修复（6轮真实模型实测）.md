# 群聊思考过程「流式很长、完成后消失」根因排查与 6 轮真实模型实测（v1.7.20）

> 模型：硅基流动 `deepseek-ai/DeepSeek-V3.2`（thinking=high）
> 实测方式：Playwright 启动真实 Electron 应用 + 真实 opencode sidecar + 真实模型（不是 mock）
> 仓库版本：1.7.19 → **1.7.20**（PATCH：均为缺陷修复，无新能力）

## 一、用户报告

> 在项目群里提问，所有群成员处理过程中都会不断流式输出很长（怀疑是思考过程内容），但任务完成后这部分内容又不会出现了。

排查后确认这不是一个 bug，而是**四个叠加的缺陷**，用户看到的现象是它们的组合结果。

## 二、根因（都用真实 sidecar 的事件/落库对账确认）

### 1. 流式阶段：思考被当成正文推给界面（主因，直接解释「不断流式输出很长」）

opencode 的 `message.part.delta` 事件对「正文 part」和「思考 part」推来的 `field` **都是 `'text'`**
（`field` 是 part 的 `text` 属性名，不是 part 类型）。而 `packages/core/src/index.ts` 原来按
`field === 'reasoning'` 判断思考，于是：

- 思考增量全部被累加进 `stream.text`，渲染在**正文气泡**里 → 用户看到正文不断刷很长；
- 完成后落库的却是 `type: 'reasoning'` part，转由「思考过程」折叠条展示 → 正文骤减，体感就是「内容消失了」。

抓到的原始事件序列（`version 1.18.26`）：

```
{"e":"updated","part":"prt_...","type":"reasoning","len":0}      ← 先声明 part 类型
{"e":"delta","part":"prt_...","type":"reasoning","field":"text"} ← 但 field 仍是 text
{"e":"delta","part":"prt_...","type":"text","field":"text"}
落库 parts = ["step-start","reasoning(97)","text(29)","step-finish"]
```

**修复**：新增 `streamPartTypes`（partID → part.type，由 `message.part.updated` 记录），delta 一律按
part 类型归类；类型未知时才退回 `field` 判断（兼容旧 sidecar）。完成信号时一并回收，防内存缓增。

### 2. 落库阶段（群成员走 `jeff_delegate` 委派时）：只回文本，思考与工具整段丢弃

leader 有一种派发方式是调用 `jeff_delegate` 工具（R3/R6 实测模型大量使用它）。`Delegator.delegate`
写回群消息时只做了 `parts.filter(p => p.type === 'text')`，成员辛辛苦苦流式输出的 reasoning / tool 全部丢在
meta 之外。

对照证据：opencode 自己库里成员消息是 `reasoning(147)+tool(read)` 与 `reasoning(304)+text(115)`，而群里落库的
成员气泡 `reasonLen=0 tools=[]`。

**修复**：抽出共用函数 `extractReplyParts(reply)`（正文/思考/工具三路），`GroupChat.runTurn` 与
`Delegator.delegate` 共用；委派结果气泡的 meta 现在同时带上 `reasoning` 与 `tools`。

> 注：另一条派发路径（leader 在回复里写 `@成员名`）走 `runTurn`，本来就落了 reasoning/tools，没问题。
> 只有 `jeff_delegate` 这条路径丢数据，所以问题表现为「有时候有、有时候没有」。

### 3. 中间工具步的「正文」被整段丢弃（另一类模型更常见）

opencode 一轮「模型→工具→模型」会建多条 assistant 消息，`sendMessage` 只返回最后一条。
关闭 thinking 的模型（或有 preamble 习惯的模型）会把工具调用前的推导写成**正文 text part**，
只返回最后一条就会丢。`mergeTurnParts` 原来只合并 reasoning/tool，现在把「中间步（非最后一条、且带 tool）的
正文」转成 reasoning part 保留；私聊历史 `mapSessionMessages` 同规则，保证「流式看到的」与「历史回放的」位置一致。

### 4. 顺带发现：群聊内容从未进入记忆索引

`onReplyDone` 用 `chatMessageRepo.listByScope('group:<projectId>')` 取消息，但群消息实际 scope 是
`group:<projectId>:<threadId>`，精确查询永远为空 → 群聊内容一条都进不了 FTS 记忆库。
新增 `listByScopePrefix`（LIKE 通配符已转义），索引 scope 仍写 `group:<projectId>`（与 `jeff_memory` 检索口径一致）。

## 三、6 轮真实模型实测

测试台：`.tmp/live6/`（临时脚本，不提交）——预置 provider（硅基流动 `deepseek-ai/DeepSeek-V3.2`，thinking=high）、
1 个群（群主「指挥官」+ 3 名 worker）、1 个私聊智能体、带素材的工作空间。

每轮采集两类证据并互相校验：
- **流式帧**：每 400ms 采样流式气泡的正文长度 / 思考折叠区长度（DOM）；
- **落库结果**：`group:history` / `chat:history` 的 `text` / `reasoning` / `tools`。
判定标准：**流式期间出现过的内容（正文与思考两条通道分别判定），完成后必须仍能找到**。

| 轮次 | 场景 | 结果 | 关键证据 |
|------|------|------|----------|
| R1 | 群聊首问（群主直答） | ✅ 29.6s | 流式期间正文恒 1 字、折叠区 2→135；落库 text 32 / reasoning 135 |
| R2 | 群内 @ 成员直达 | ✅ 1.6m | worker 折叠 196、leader 折叠 509；落库 reasoning 196/688 + tools |
| R3 | 群内多轮长任务（工具+派发） | ✅ 6.5m（修复委派后复测） | 成员 reasoning 430/445/666 + tools=[glob,read,write] 全部落库 |
| R4 | 单独私聊简单问答 | ✅ 37s | 折叠 203 → 落库 reasoning 203 |
| R5 | 单独私聊多轮工具任务 | ✅ 1.4m | 4 个工具步 reasoning(46/17/129/53) + 最终答复 327 字落库 |
| R6 | 群内工具长任务回归 | ✅ 8.2m | 成员 reasoning 1096/1020、工具 12/9 个全落库；产出 `清单.md` |

修复前后对比（同一场景 R1，同一模型）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 流式期间正文长度峰值 | 163 字（整段推导刷在正文里） | 32 字（正文只出最终答复） |
| 流式期间思考区 | 0 → 最后才出现 | 全程在折叠区，2→135 字 |
| 委派成员 reasoning 落库 | 0（全部丢弃） | 430～1096 字 |

### 修复前复现证据（R1，未修复版本）

```
t=27773 指挥官 body=  2 fold=  0   ← 推导以正文推来
t=31139 指挥官 body=123 fold=  0
t=31559 指挥官 body=132 fold=123   ← 落库判定为 reasoning 后才出现折叠区
落库：text=39 / reasoning=123      ← 正文里的 123 字推导「消失」
```

## 六、遗留与观察

- 流式气泡的思考区只显示**当前那条消息**的思考；一轮里多次「模型→工具→模型」时，前一步的思考会在流式过程中被
  后一步覆盖（完成后由折叠区完整呈现）。属展示层取舍，不影响数据完整性。
- R6 中群主会主动 `jeff_delegate` 派发而不是写 `@成员名`；两条路径现已一致，遵循模型自身选择，未强制改写。
