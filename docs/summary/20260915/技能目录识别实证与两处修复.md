# 技能目录识别实证：智能体读的就是 `~/.agents/skills`（附两处真问题的修复）

> 2026-09-15 · v1.8.6 · 回归完整十轮真模型 E2E（`.tmp/live14/`，11/11 通过）+ 单测 258/258

## 命题

用户问：给智能体发「调用 思源笔记 技能读取 ID `20260914145636-ifd8y0u` 文档」时，
它读的是不是 `~/.agents/skills` 下的技能？如果不是就修，**所有技能都应该在这个目录下读**。

**结论：是。** 而且顺着这条链路测下去，挖出并修掉两个真问题（都不在「读哪个目录」上，
但在同一条链路上）：内置技能漏在目录之外、管家小杰有条 `task` 后门可以绕过「没有命令工具」。

## 一、结论怎么来的（不靠猜，四层证据）

### 1. 反编译打包进去的 opencode，看清技能发现逻辑

`opencode` 是 bun 单文件二进制，直接读字符串能看到技能发现函数：

```js
// 隐式扫描：只有 !disableExternalSkills 时才做
if (!B) { Z.push('.claude'…); Z.push('.agents'…); …project 向上找… }
// 抓 opencode 自己的配置目录
for (const O of yield*j.directories()) …
// ⭐ 显式挂载：在 if(!B) 之外，永远执行
for (let O of N.skills?.paths ?? []) { … }
```

也就是说 `OPENCODE_DISABLE_EXTERNAL_SKILLS=1`（`sidecar/manager.ts`）**管不到** `skills.paths`。
Jeff 的 `oc/configWriter.ts` 把 `~/.agents/skills` 写进 `skills.paths`，所以两条并不冲突：
前者挡掉 `~/.claude/skills` 等外部目录，后者是用户技能进模型的唯一入口。

### 2. 起真 sidecar 对账（两个 opencode 版本都测）

| 二进制 | 环境 | `/skill` 结果 |
|--------|------|---------------|
| `~/.opencode/bin/opencode`（1.18.26） | 带 `OPENCODE_DISABLE_EXTERNAL_SKILLS=1` | 52 个：50 个来自 `~/.agents/skills` + `jeff-usage` + opencode 内置 |
| 打包的 `resources/oc-bin/linux-x64/opencode`（**1.18.30，实际发布的那个**） | 同上 | 51 个，`missing: []`（用户目录下每个技能都进了清单） |

逐个比对 location：`~/.agents/skills/*` 里的 50 个一个不漏；
唯一的例外是 opencode 二进制里自带的 `customize-opencode`（`<built-in>`，改不动也不该改）。

**顺带确认了那个开关为什么必须留着**：本机 `~/.claude/skills` 有 15 个技能，与
`~/.agents/skills` **撞名 11 个**（`siyuan-read`、`docx`、`pdf`、`xlsx`…）。
不关掉隐式扫描，Claude Code 那套会混进 Jeff 的技能清单——「智能体读的是哪一份 siyuan-read」
就成了开盲盒。

### 3. 十轮真模型 E2E（`.tmp/live14/`，11/11 绿）

| 轮次 | 场景 | 结果 |
|------|------|------|
| R0 | 真 sidecar 的 `/skill` 清单 vs `~/.agents/skills` 实际目录对账（不经模型） | 52 = 51 用户目录 + 1 内置，`missing: []`，无旁路来源 |
| R1 | **用户原话**，发给「描述里点名技能」的智能体（V3.2） | `skill{siyuan-read}` → `bash`（`workdir=~/.agents/skills/siyuan-read`）→ 文档正文 |
| R2 | 同一句话，发给**描述完全不提技能**的智能体（开箱即用） | 模型自己从技能清单里发现并调用，读到正文 |
| R3 | 追问「siyuan-read 的 SKILL.md 绝对路径」 | 答 `/home/xujian/.agents/skills/siyuan-read/SKILL.md` |
| R4 | 同会话追问文档细节（根分区占用、npm 错码） | 97% / `EUNSUPPORTEDPROTOCOL`，来自文档而非编造 |
| R5 | 项目群：`@资料小丁` 让成员用技能取资料回群 | 成员读文档并把要点带回群，群主汇总 |
| R6 | 小杰（无 bash/edit/write）同一请求 | 如实说「这条我直接做不了」并解释原因（见下「修复二」） |
| R7 | 调用一个不存在的技能 | `skill` 工具报错 → 列出全部可用技能，不编内容 |
| R8 | 搜索技能（siyuan-search） | 返回真实文档 ID（`\d{14}-[a-z0-9]{7}` 形状） |
| R9 | **用户真实模型 `opencode-go/deepseek-flash`** 跑用户原话 | 24.9s 内 `skill` → `bash` → 正文摘要 |
| R10 | 同会话追问报错码 | 只回 `EUNSUPPORTEDPROTOCOL`（本轮新增文本，不是复述历史） |

测试台的坑（都属「预期错了」而非产品错，记下来免得下次重踩）：
① 断言不能取**整段会话**的 assistant 文本——上一轮的回复会让本轮「什么都没答」也判绿（第一版就假绿了 R10）；
② 群窗口没有 `chat-window` 这个 testid（那是私聊的），群窗口认 `group-info-btn`；
③ 冷启动第一次 `/skill` 要现场扫 51 个技能目录，超时给到 60s 并重试；
④ 群回合含「群主 → 委派成员 → 群主汇总」三次模型调用，实测可跑 10 分钟，超时要给 25 分钟。

## 二、修复一：内置技能漏在「技能目录」之外

**问题**：模型看到的技能里，`jeff-usage`（Jeff 自己的使用说明技能）写在应用私有目录
`<数据目录>/oc-home/config/opencode/skills/`——那是 opencode 扫自己配置目录扫出来的，
属于「技能目录」之外的唯一例外，与「所有技能都在 `~/.agents/skills`」相矛盾。

**改法**：`writeUsageSkill()` 改写 `~/.agents/skills/jeff-usage/`，并清掉旧位置的残留
（不清会同名两来源）。每次启动重写，所以随 WebDAV 同步/恢复来的旧副本会被自动纠正。

**连带必须改的**：备份的「新机器保护」判定原来是「本地目录为空」，现在本机上一定有个
`jeff-usage`，判定会失效 → 新机器首次备份会把远端整套技能当「多余项」删（先被 30% 熔断拦住，
但体验与语义都变了）。改为**只看用户自己的技能**：本地只剩 `jeff-usage` 时照旧报错跳过。

回归：`tests/skills-dir.test.ts`（新增 6 例）+ `tests/skills-sync.test.ts`（新增「只剩内置技能」一例）。

## 三、修复二：小杰的 `task` 后门（live14 R6 实测挖出）

**问题**：小杰的 agent 定义里禁了 `bash`/`edit`/`write`/`patch`（管家不该能任意写盘/执行命令），
但 `task`（派子代理）还开着，而子代理带**全套**工具。实测：

1. 小杰调 `skill{siyuan-read}` 拿到 SKILL.md；
2. 发现自己没法跑脚本 → 调 `task` 派个子代理；
3. 子代理跑 `bash python3 scripts/export_md.py …` 把文档取回来；
4. 小杰把结果当自己的成果汇报——「管家没有命令工具」整条约束形同虚设。

**改法**：`XIAOJIE_DISABLED_TOOLS` 加 `task`（`packages/core/src/agents/registry.ts`）。
子代理委派是项目群 leader 的活（`jeff_delegate`），不是管家的。

**修后实测（R6 复跑）**：小杰这一轮再无 `bash/edit/write/patch/task`（日志断言），
也没有声称读到正文；它试了只读的 `read`/`grep`/内置浏览器几条路，最后如实回答
「这条我直接做不了」并解释：①自己没有命令/文件工具跑不了技能脚本；②想用内置浏览器绕过，
但那个接口只收 POST、浏览器只能 GET。

## 五、留给下次的两点

- **冷启动第一次技能扫描有成本**：51 个技能目录、每个 SKILL.md 都要解析，第一次 `/skill` 实测可超 15s。
  首轮对话会分摊到这部分延迟。技能越多，每轮 system prompt 里的技能清单（name+description）也越大——
  用不到的技能建议从目录里挪走，而不是留在那儿。
- **技能配置文件的敏感性**：思源技能把 token 放在技能目录的 `siyuan.env`，模型为了排查会 `read` 它，
  于是 token 会出现在模型上下文与 `<数据目录>/logs/debug-*.log` 里。技能自己读文件是预期行为，
  但写技能时应尽量让脚本只读配置、并把「不要读 env 文件」写进 SKILL.md（`docs/skills.md` 已记）。
