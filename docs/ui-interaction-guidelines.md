# Jeff UI 与交互设计规范

适用于桌面端与 Android。新增或改动任何界面前先阅读本文件，明确用户任务、数据归属、状态变化和失败路径；完成后以实际布局和服务端/数据库结果验收。

## 1. 先说明对象和用户任务

- 页面首屏应让用户看出当前编辑的对象、当前生效状态和下一步操作。一个页面突出一个主要任务。
- 配置必须存放在它所属的对象上：Agent 的个人默认属于 Agent；群规则、成员职责和成员级覆盖属于项目群；CLI 路径和凭据属于当前电脑。
- 名称描述用户管理的对象。“执行引擎”是用户选择项；进程、端口和后台服务是诊断信息。
- 同一个 Agent 在不同项目群可以有不同职责；群内身份不得污染个人简介、个人 System Prompt 或私聊。
- Jeff 工具扩展 Agent 的能力，不按内置身份、姓名或通讯录分类隐藏操作。真实作用域、调用者身份和输入校验仍由系统保证。

## 2. 信息结构随规模增长

- 可增长的同类对象使用单一选择器或受控列表，并只展示当前对象的详情；不得为每个 CLI、提供商或成员同时展开一整页设置卡片。
- 选项超过 6 个时提供搜索。桌面菜单高度不超过 320px 或当前可见空间，并在菜单内部滚动；打开时避让窗口边界。
- 长名单采用“列表 + 当前成员详情”，避免一次展开所有成员的职责和模型表单。
- 首屏只展示常用操作。路径、原生配置、日志、版本和调试项放在有明确名称的折叠区；确有错误时可直接指出相关诊断入口。
- 页面允许合理纵向滚动；避免横向滚动、卡片套卡片、重复说明和为了填满空间增加的装饰。
- 备份与恢复入口仍统一放在“设置 → 同步”；结构化数据进入既有同步，不复制到功能页。

## 3. 控件、密度和主题

- 复用项目现有的颜色、间距、按钮、字段、选择器、提示和对话框组件。使用主题 token，不用浏览器默认白底控件破坏暗色主题。
- 正文字号约 14px，辅助文字 12–13px，区块标题约 16px，页面标题约 20px；正文行高约 1.5。中文使用系统无衬线字体。
- 以 8px 为间距基准：控件间 8–12px，字段间约 16px，区块间约 24px。桌面常规控件高度约 36px；手机主要点击目标至少 44px。
- 状态同时提供文字和视觉提示；不能只用颜色表达成功、失败、停用或未检测。
- 窄窗时字段和操作换行、长路径可查看/复制全文；不得让核心操作被裁切或页面横向溢出。

## 4. 状态与数据安全

- 覆盖初始、加载、空、成功、失败、禁用和不可用状态。区分“检测到程序”“协议可用”“已认证”“真实模型请求成功”，不得把前者写成后者。
- 保存按钮明确展示保存中、已保存或失败。失败时保留用户输入并在操作附近解释原因；不能出现失败后仍显示成功的乐观状态。
- 未保存内容在切换对象、切换引擎或关闭抽屉时必须受到保护。给出“保存并继续／放弃更改／取消”或等价的明确操作。
- “继承个人设置”和“显式覆盖”应清楚区分；恢复继承是可理解、可测试的明确动作，不用含义模糊的空值按钮。
- 配置变更影响范围应紧邻保存动作说明。引擎变更不静默迁移旧会话，不自动降级或重发；旧会话仍能识别原引擎。
- 对异步操作防重复提交，反馈结果并允许恢复；破坏性动作说明影响范围。

## 5. 桌面与手机一致性

- 同一领域数据和状态含义在桌面与手机保持一致；为手机重排交互，不把桌面窄缩成不可读的多列表格。
- 选择 Agent 或项目群成员后，编辑内容必须跟随当前选中对象。切换对象时重新加载其配置，不能显示上一位成员的草稿。
- 手机控制桌面 CLI 时明确显示“当前连接电脑”的检测/保存事实；不能暗示 CLI 安装在手机本机。

## 6. 可访问性与可理解性

- 所有输入有可见标签或可访问名称；主要操作可键盘聚焦，焦点顺序与视觉顺序一致。
- 下拉、弹窗和抽屉提供明确标题、关闭方式、禁用原因和焦点反馈。状态更新用适当的 `role="status"` / `role="alert"`。
- 文案使用用户任务语言；技术细节按需渐进展开。避免在同一页面反复解释相同规则。

## 7. 设计与验收流程

1. 编码前记录用户任务、对象归属、状态变化和边界场景；数据关系不清时先核实领域模型。
2. 先做可审阅的静态结构/原型，再接真实 IPC、同步和运行行为；不得用只有截图好看的本地假数据替代真实交互。
3. 至少检查正常、空、加载、错误、未保存、不可用和长内容状态；验证保存后重新读取的事实，而非只断言 DOM 文案。
4. 桌面按窄、中、宽窗口和亮/暗主题检查；Android 按 360、390、430 CSS px 检查。覆盖长名、长路径、较多选项、成员和空状态。
5. 检查键盘操作、焦点、滚动、边界裁切、横向溢出、按钮禁用和异步错误；保留关键截图，目检后再收尾。
6. 报告说明改了哪些交互、验证了哪些布局与状态、哪些真实链路尚未具备条件；不把 UI 通过说成真实模型或安装版通过。

## 8. 反例与正例

- 反例：每新增一个引擎就在页面追加一张配置卡片。正例：一个引擎下拉，显示当前所选引擎的配置与诊断。
- 反例：模型提供商作为独立执行引擎并始终显示。正例：只在“OpenCode（Jeff）”的详情中编辑 Jeff 管理的提供商。
- 反例：把群主/worker 写进 Agent 个人 Prompt。正例：将群主关系和每位成员的职责保存到对应群。
- 反例：群成员的模型覆盖写回 Agent。正例：群内显式覆盖只影响该群，恢复继承后实时跟随个人默认。
